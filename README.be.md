## Першае наладжванне

### Наладжванне шлюза
1. Адкрыйце **Settings > Devices & services > Add integration** і выберыце
   **HDL Buspro**.
2. Увядзіце адрас хоста шлюза і порты UDP. Порт `6000` - гэта звычайны па змоўчанні.
3. Увядзіце невыкарыстаны адрас Home Assistant Buspro у фармаце `subnet.device`.
   Па змоўчанні гэта `200.200`; ён не павінен адносіцца да іншага прыстасавання Buspro.

### Дабаванне прыстасаванняў
Пасля завяршэння наладжвання шлюза:

1. Адкрыйце **Settings > Devices & services > HDL Buspro > Configure**.
2. Націсніце **Add device**, каб дадаць фізічны модуль Buspro.
3. **Выберыце тып прыстасавання** (Relay, Dimmer, Cover, Climate, Sensor, і т.д.).
4. **Выберыце дакладную модэль**, якая адпавядае вашаму абсталяванню.
5. **Увядзіце адрас Buspro** у фармаце `subnet.device` (напрыклад, `1.5`).
6. **Увядзіце назву прыстасавання** (напрыклад, "Асвятленне гасцінай").
7. **Назавіце кожны канал** — пакіньце пустым, каб адключыць канал.
8. Націсніце **Save**.

Home Assistant аўтаматычна групіруе сутнасці па фізічным модулях у Рэестры прыстасаванняў.

**Для прыкладаў наладжвання UI і YAML для ўсіх тыпаў прыстасаванняў гл. [DEVICE_EXAMPLES.md](docs/en/DEVICE_EXAMPLES.md).**

### Рэдагаванне прыстасаванняў

Каб змяніць існуючае прыстасаванне, адкрыйце **Configure > Edit device**. Вы можаце:
- Перайменаваць прыстасаванне
- Перайменаваць, ўключыць або адключыць асобныя каналы
- Змяніць модэль (гэта можа змяніць колькасць каналаў)
- Цалкам выдаліць прыстасаванне

Прыстасаванні, якімі кіруе UI, падтрымліваюць поўнае рэдагаванне. Старажытныя прыстасаванні YAML могуць паказаць элементы кіравання назвамі рэестра, але іх канфігурацыя пратакола ўсё яшчэ павінна быць змененая ў YAML. Перазапусціце Home Assistant пасля змены YAML.

### Хуткі прыклад: Дабаванне 4-канальнага модуля реле

1. Модэль: `HDL-MR0410.431` (4 канала реле)
2. Адрас Buspro: `1.10`
3. Назва прыстасавання: "Рэле ў пакоі"
4. Назвы каналаў: "Асвятленне столі", "Бакавая лямпа", "", "Вентылятар"
5. Націсніце **Save**

Home Assistant аўтаматычна стварае сутнасці: `light.room_relays_ceiling_light`, `light.room_relays_wall_lamp`, `switch.room_relays_fan`

Для поўных прыкладаў UI і YAML для ўсіх тыпаў прыстасаванняў гл. **[DEVICE_EXAMPLES.md](docs/en/DEVICE_EXAMPLES.md)**.

## Опцыі наладжвання

Інтэграцыя buspro падтрымлівае як **наладжванне на аснове UI**, так і **наладжванне YAML**:

### Наладжванне UI
Самы простыспосаб дадаць прыстасаванні — гл. **[DEVICE_EXAMPLES.md](docs/en/DEVICE_EXAMPLES.md)** для пакроковых прыкладаў ўсіх тыпаў прыстасаванняў.

### Наладжванне YAML  
Інтэграцыя падтрымлівае два ўзаемадапаўняльныя падхода YAML:
- **Entity-Centric** (Legacy) — асобныя файлы сутнасцей, арганізаваныя па дамене
- **Device-Centric** (Modern) — поўныя вызначэнні прыстасаванняў з усімі каналамі

**Для поўнай дакументацыі YAML, прыкладаў і лепшых практык гл. ## Зломлівыя змены ў 2.2.0

Прачытайце гэты раздзел перад абнаўленнем з 2.1.x.

> [!WARNING]
> Гэта выпуск змяняе ўласнасць прыстасавання, стварэнне каналаў, семантыку
> падзей панелі і ўбудаваны канструктар Python. Завяршыце контрольны спіс
> абнаўлення перад выдаленнем старажытнага YAML.

1. **Прыстасаванні, специфічныя для ўстаноўкі, больш не ўбудаваны ў інтэграцыю.**
   Адрасы прыстасаванняў, іхныя назвы, прызначэнні каналаў і колькасць прыстасаванняў цяпер адносяцца да опцыі запісу канфігурацыі або Рэестра прыстасаванняў Home Assistant. Каталог прыстасаванняў змяшчае толькі магчымасці абсталявання.

2. **Модулі реле, якімі кіруе UI, выкарыстоўваюць іхны фізічны лік каналаў.**
   `HDL-MR1210.433` заўсёды паказвае 12 слотаў каналаў, а `HDL-MR1610.433` заўсёды паказвае 16. Існуючае прыстасаванне не можа быць зменшана ніжэй фізічнай колькасці каналаў яго модэлі.

3. **Пустая назва канала адключае канал.**
   Адключаныя каналы не ствараюцца, не ствараюць аб'екты пратакола і пазначаны як адключаныя інтэграцыяй у Рэестры сутнасцей. Увод назвы зноў ўключае канал.

4. **Дакладная модэль кантралюе ствараемыя сутнасці.**
   Абагульняная `HDL panel` не мае вядомай колькасці кнопак. Выберыце фізічную модэль, каб стварыць падзеі кнопкі. Змена модэлі перазагружае запіс конфігурацыі.

5. **Home Assistant мае свой адрас Buspro.**
   Існуючыя запісы канфігурацыі перамяшчаюцца на `200.200`. Гэты адрас павінен быць невыкарыстаны ў сеткі Buspro і можа быць зменены пад **Configure > Gateway settings**.

6. **IP-адрас крыніцы пакета больш не ўзвёрдзены.**
   Інтэграцыя вывядзе яго з маршруту на наладжаны шлюз. Хост Home Assistant з мноцвіма інтэрфейсамі павінен маршрутызаваць шлюз праз прызначаны інтэрфейс LAN.

7. **Падзеі дзейнасцей панелі цяпер дэкодаваны.**
   Аўтаматызацыя, якая карыстае старыя необработаныя значэнні дзейнасцей, павінна быць праверана. Падзеі выкарыстоўваюць `channel_on`, `channel_off`, `channel_level`, `scene`,
   `universal_switch_on`, або `universal_switch_off`, з атрыбутамі мэты і рэзюме, дзе яны могуць быць вырашаны.

8. **Убудаваны API Python змяніўся.**
   Прамыя карыстальнікі `pybuspro.Buspro` павінны абяспечыць `client_address`; гл.
   [pybuspro/README.md](pybuspro/README.md).

Інтэграцыя ўсё яшчэ чытае старажытныя сутнасці YAML падчас міграцыі. Не трымайце адзін і той жа фізічны канал як ў YAML, так і ў наладжванні, якім кіруе UI, таму што гэта можа стварыць дублёваныя сутнасці і дублёваныя подпіскі пратакола.

## Контрольны спіс абнаўлення

1. Перазапусціце Home Assistant пасля замены адзінаткавага кампанента.
2. Адкрыйце **Settings > Devices & services > HDL Buspro > Configure**.
3. Праверыце хост шлюза, порты і невыкарыстаны адрас Home Assistant Buspro.
4. Адкрыйце кожнае фізічнае прыстасаванне і выберыце яго дакладную модэль.
5. Праверыце кожну назву канала реле. Пустыя каналы наўмсна заставаюцца адключанымі.
6. Праверыце аўтаматызацыю, якая карыстае падзеі дзейнасцей панелі.
7. Выдаліце або каментуйце перамешчаныя сутнасці YAML толькі пасля таго, як іхныя замены, якімі кіруе UI, захавалі чаканыя ID сутнасцей.

## Наладжванне шлюза

Дадайце **HDL Buspro** з **Settings > Devices & services** і наладжце:

- **Host**: назва хоста шлюза HDL IP або адрас IPv4.
- **Port**: первічны порт UDP, звычайна `6000`.
- **UDP send/receive ports**: змяняйце гэты толькі для нестандартнага шлюза.
- **Home Assistant Buspro address**: невыкарыстана `subnet.device` ідэнтычнасць, напрыклад па змоўчанні міграцыі `200.200`.

UDP не мае ўсцісканага сувязі. Наладжванне правяраць распазнаванне адрасаў, маршрутызацыю і стварэнне лакальнага разёма прыёму без мяркавання, што прыстасаванне існуе ў жаснакодзеным адрасе Buspro.

## Кіраванне прыстасаваннямі

Адкрыйце **Configure** ў інтэграцыі і выберыце:

- **Gateway settings**, каб абнавіць параметры сеткі і ідэнтычнасць клієнта.
- **Add device**, каб выбраць тып прыстасавання, модэль, адрас Buspro і назвы каналаў або магчымасцей.
- **Edit device**, каб перайменаваць каналы, ўключыць або адключыць каналы, выдаліць прыстасаванне, якім кіруе UI, або выправіць модэль існуючага прыстасавання рэестра.

Фізічныя адрасы паказаны ў Home Assistant як серыйны нумар прыстасавання.
Сутнасці, якія адносяцца да адного фізічнага модуля, прыўзяты да адной запісі Рэестра прыстасаванняў.

## Помацнік абслугоўвання каталога

Каб параўнаць каталог інтэграцыі з абслугоўваным афіцыйным спісам модэляў HDL, запусціце:

```bash
python3 custom_components/buspro/tools/check_catalog_models.py
```

Помацнік чытае `custom_components/buspro/devices/official_models.json` і выводзіць:

- афіцыйныя мадэлі, якія адсутны ў `DEVICE_CATALOG`
- мадэлі каталога, якія адсутны ў афіцыйным спісе
- віртуальныя інтэграцыйна-толькі абагульненыя мадэлі

Выкарыстоўвайце рэжым сцішцяня для праверак у стылі CI (ненулявы выхад, калі афіцыйныя мадэлі адсутны ў каталога):

```bash
python3 custom_components/buspro/tools/check_catalog_models.py --strict
```

## Паведзеныя сутнасцей

### Реле

Адзін агульны координатар запытвае статус реле адзін раз за фізічны модуль і распаўсюджвае адказ ва ўсе ўключаныя сутнасці каналаў. Адключаныя каналы не падпісваюцца на шыну і не запытваюць яе.

### Панелі

Вядомыя панелі кнопак ствараюць адну сутнасць `event` для кожнай фізічнай кнопкі, падзею `Action` і датчык `Last action`. Сутнасці падзей кнопак UI прадстаўляюць атрыманыя фізічныя тэлеграмы кнопак Buspro; яны не імітуюць фізічнае націсканне.

### Дыміры

Падтрыманыя дыміры могуць паказаць сувязь, максімальную яскравасць на канал, тып нагрузкі і мінімальную яскравасць, паведамленую пратаколам. `Not reported` азначае, што прыстасаванне вярнула дажыніка пратакола, а не прыдатнае значэнне.

### Кантролер логікі

`HDL-MCLog.431` паказвае сувязь толькі для чытання, версію прашыўкі, апошнюю бачыны і сутнасці логічных падзей. Некаторыя прашыўкі не адказваюць на стандартны запыт прашыўкі; у гэтым выпадку сутнасць прашыўкі заставаецца недаступнай. Логічныя блокі не могуць быць запісаны, таму што іхнія змены могуць пераписаць праграмаванне кантролёра.

## Наладжванне YAML (Legacy)

Наладжванне прыстасавання YAML цалкам падтрымліваецца паралельна з кіраваннем шлюза запісу канфігурацыі. Вы можаце вызначыць лямпы, завесы, выключы, вентылятары, клімат, датчыкі і бінарныя датчыкі праз YAML, у той час як шлюз кіруецца UI інтэграцыі.

**Заўвага**: Новыя прыстасаванні павінны выкарыстоўваць UI інтэграцыі **Configure > Add device** замест YAML, так як ён забяспечвае групіванне прыстасаванняў, магчымасцей на аснове модэлі і кіраванне станом канала. YAML рэкамендуецца для:
- Прыстасаванняў з нестандартнымі або старажытнымі профіламі
- Міграцыя з старэйшых інтэграцыяў Buspro
- Сложная аўтаматызацыя або шаблоны датчыкаў

### Прыклад сінтаксісу YAML

Дадайце ў ваш `configuration.yaml`:

```yaml
light:
  - platform: buspro
    devices:
      "1.5.1":
        name: "Ceiling light"
        dimmable: true
      "1.5.2":
        name: "Wall lamp"
        dimmable: false

cover:
  - platform: buspro
    devices:
      "2.10.1":
        name: "Living room curtain"
        running_time: 45

climate:
  - platform: buspro
    devices:
      "3.1":
        name: "Bedroom climate"
        profile: "ac"
```

### Наладжванне платформы

Кожная платформа (`light`, `cover`, `fan`, `climate`, `sensor`, `binary_sensor`, `switch`) прымае:

| Ключ | Тып | Апісанне |
| --- | --- | --- |
| `devices` | dict | Абавязкова. Адлюстраванне адрасаў Buspro на канфігурацыі прыстасаванняў. |
| `running_time` | int | Час пераходу па змоўчанні ў секундах (0 = без переходу). Выбіраецца па прыстасаванні. |
| `ack_retry_enabled` | bool | Паўторныя адпраўкі пры адсутнасці ACK (па змоўчанні платформы; выбіраюцца па прыстасаванні). |

Кожны ключ прыстасавання - гэта **адрас Buspro** у фармаце:
- **Light, cover, fan, switch**: `subnet.device.channel` (напрыклад, `1.5.2`)
- **Climate, sensor, binary_sensor**: `subnet.device` (напрыклад, `3.1`)

Кожная канфігурацыя прыстасавання падтрымлівае:
- `name` (абавязкова): Назва дысплея
- `running_time`, `dimmable`, `ack_retry_enabled` (спецыфічна для платформы, опцыянальна)
- `profile` (опцыянальна, для датчыкаў клімату — напрыклад, `"ac"`, `"floor_heating"`)
- `object_id` (опцыянальна): Entity ID slug
- `unique_id` (опцыянальна): Для ручнога кіравання рэестрам сутнасцей
