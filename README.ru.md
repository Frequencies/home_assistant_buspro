## Первая настройка

### Конфигурация шлюза
1. Откройте **Параметры > Устройства и сервисы > Добавить интеграцию** и выберите
   **HDL Buspro**.
2. Введите адрес шлюза и порты UDP. Порт `6000` — обычное значение по умолчанию.
3. Введите неиспользуемый адрес Home Assistant Buspro в формате `subnet.device`.
   Значение по умолчанию — `200.200`; он не должен принадлежать другому устройству Buspro.

### Добавление устройств
После завершения настройки шлюза:

1. Откройте **Параметры > Устройства и сервисы > HDL Buspro > Конфигурация**.
2. Нажмите **Добавить устройство**, чтобы добавить физический модуль Buspro.
3. **Выберите тип устройства** (Реле, Диммер, Завеса, Климат, Датчик и т. д.).
4. **Выберите точную модель**, соответствующую вашему оборудованию.
5. **Введите адрес Buspro** в формате `subnet.device` (например, `1.5`).
6. **Введите имя устройства** (например, "Люстра в гостиной").
7. **Назовите каждый канал** — оставьте пустым, чтобы отключить канал.
8. Нажмите **Сохранить**.

Home Assistant автоматически группирует объекты по физическому модулю в реестре устройств.

**Примеры конфигурации пользовательского интерфейса и YAML для всех типов устройств см. в [DEVICE_EXAMPLES.md](docs/en/DEVICE_EXAMPLES.md).**

### Редактирование устройств

Чтобы изменить существующее устройство, откройте **Конфигурация > Редактировать устройство**. Вы можете:
- Переименовать устройство
- Переименовать, включить или отключить отдельные каналы
- Изменить модель (что может изменить количество каналов)
- Полностью удалить устройство

Устройства, управляемые пользовательским интерфейсом, поддерживают полное редактирование. Устаревшие устройства YAML могут предоставлять элементы управления наименованием реестра, но их конфигурация протокола по-прежнему должна изменяться в YAML. Перезагрузите Home Assistant после изменения YAML.

### Быстрый пример: добавление 4-канального модуля реле

1. Модель: `HDL-MR0410.431` (4 канала реле)
2. Адрес Buspro: `1.10`
3. Имя устройства: "Реле комнаты"
4. Названия каналов: "Люстра", "Настенная лампа", "", "Вентилятор"
5. Нажмите **Сохранить**

Home Assistant автоматически создает объекты: `light.room_relays_ceiling_light`, `light.room_relays_wall_lamp`, `switch.room_relays_fan`

Полные примеры пользовательского интерфейса и YAML для всех типов устройств см. в **[DEVICE_EXAMPLES.md](docs/en/DEVICE_EXAMPLES.md)**.

## Параметры конфигурации

Интеграция buspro поддерживает как **пользовательский интерфейс**, так и **конфигурацию YAML**:

### Настройка пользовательского интерфейса
Самый простой способ добавления устройств — см. **[DEVICE_EXAMPLES.md](docs/en/DEVICE_EXAMPLES.md)** для пошаговых примеров всех типов устройств.

### Конфигурация YAML  
Интеграция поддерживает два дополняющих подхода YAML:
- **Ориентированная на объекты** (Устаревшая) — отдельные файлы объектов, организованные по доменам
- **Ориентированная на устройства** (Современная) — полные определения устройств со всеми каналами

**Для полной документации YAML, примеров и лучших практик см. [DUAL_MODE_YAML.md](docs/en/DUAL_MODE_YAML.md)** (также доступно на [Беларуская](docs/be/DUAL_MODE_YAML.md) | [Deutsch](docs/de/DUAL_MODE_YAML.md) | [Español](docs/es/DUAL_MODE_YAML.md) | [Français](docs/fr/DUAL_MODE_YAML.md) | [Italiano](docs/it/DUAL_MODE_YAML.md) | [Nederlands](docs/nl/DUAL_MODE_YAML.md) | [Norsk](docs/no/DUAL_MODE_YAML.md) | [Русский](docs/ru/DUAL_MODE_YAML.md) | [Українська](docs/uk/DUAL_MODE_YAML.md))

## Критические изменения в версии 2.2.0

Прочитайте этот раздел перед обновлением с версии 2.1.x.

> [!WARNING]
> Этот выпуск изменяет владение устройствами, создание каналов, семантику событий панели
> и встроенный конструктор Python. Завершите контрольный список обновления перед
> удалением устаревшей конфигурации YAML.

1. **Устройства для конкретной установки больше не встроены в интеграцию.**
   Адреса устройств, имена, назначение каналов и количество устройств теперь принадлежат
   параметрам записи конфигурации или реестру устройств Home Assistant. Каталог устройств
   содержит только возможности оборудования.

2. **Модули реле, управляемые пользовательским интерфейсом, используют их физическое количество каналов.**
   `HDL-MR1210.433` всегда открывает 12 слотов каналов и
   `HDL-MR1610.433` всегда открывает 16. Существующее устройство не может быть уменьшено
   ниже физического количества каналов его модели.

3. **Пустое имя канала отключает канал.**
   Отключенные каналы не создаются, не создают объекты протокола и
   отмечаются как отключенные интеграцией в реестре объектов. Введение имени
   снова включает канал.

4. **Точная модель контролирует созданные объекты.**
   Универсальная `панель HDL` не имеет известного количества кнопок. Выберите физическую модель
   для создания событий кнопок. Изменение модели перезагружает запись конфигурации.

5. **Home Assistant имеет собственный адрес Buspro.**
   Существующие записи конфигурации переносятся на `200.200`. Этот адрес должен быть неиспользуемым в
   сети Buspro и может быть изменен в **Конфигурация > Параметры шлюза**.

6. **IP-адрес источника пакета больше не жестко закодирован.**
   Интеграция получает его из маршрута к сконфигурированному шлюзу. Узел Home Assistant
   с несколькими интерфейсами должен маршрутизировать шлюз через
   предполагаемый интерфейс локальной сети.

7. **События действий панели теперь декодируются.**
   Автоматизация, использующая старые значения действий, должна быть проверена. События используют
   `channel_on`, `channel_off`, `channel_level`, `scene`,
   `universal_switch_on` или `universal_switch_off`, с атрибутами целевых объектов и сводки
   где они могут быть разрешены.

8. **Встроенный API Python изменился.**
   Пользователи `pybuspro.Buspro` должны предоставить `client_address`; см.
   [pybuspro/README.md](pybuspro/README.md).

Интеграция по-прежнему читает устаревшие объекты YAML во время миграции. Не сохраняйте
один и тот же физический канал в конфигурации YAML и управляемого пользовательским интерфейсом,
так как это может создать дублирующиеся объекты и дублирующиеся подписки протокола.

## Контрольный список обновления

1. Перезагрузите Home Assistant после замены пользовательского компонента.
2. Откройте **Параметры > Устройства и сервисы > HDL Buspro > Конфигурация**.
3. Проверьте хост шлюза, порты и неиспользуемый адрес Buspro для Home Assistant.
4. Откройте каждое физическое устройство и выберите его точную модель.
5. Проверьте имя каждого канала реле. Пустые каналы намеренно остаются отключенными.
6. Проверьте автоматизацию, использующую события действий панели.
7. Удалите или добавьте комментарий к перенесенным объектам YAML только после того, как их
   управляемые пользовательским интерфейсом замены сохранили ожидаемые идентификаторы объектов.

## Настройка шлюза

Добавьте **HDL Buspro** из **Параметры > Устройства и сервисы** и настройте:

- **Хост**: имя хоста или IPv4-адрес шлюза HDL.
- **Порт**: основной порт UDP, обычно `6000`.
- **Порты отправки/получения UDP**: изменяйте только для нестандартного шлюза.
- **Адрес Buspro для Home Assistant**: неиспользуемая идентификация `subnet.device`, такая
  как стандартное значение после миграции `200.200`.

UDP не имеет подтверждения подключения. Настройка проверяет разрешение адреса, маршрутизацию
и создание локального сокета приема без предположения, что устройство существует
по жестко закодированному адресу Buspro.

## Управление устройствами

Откройте **Конфигурация** в интеграции и выберите:

- **Параметры шлюза** для обновления параметров сети и идентификации клиента.
- **Добавить устройство** для выбора типа устройства, модели, адреса Buspro и канала или
  имен возможностей.
- **Редактировать устройство** для переименования каналов, включения или отключения каналов, удаления
  управляемого пользовательским интерфейсом устройства или исправления модели существующей записи реестра.

Физические адреса показаны в Home Assistant как серийный номер устройства.
Объекты, принадлежащие одному физическому модулю, присоединены к одной записи
реестра устройств.

сообщаются как предупреждения при запуске, затем переходят к универсальному поведению `sensor_status`
для сохранения функциональности установки.

## Помощник по обслуживанию каталога

Для сравнения каталога интеграции с поддерживаемым официальным списком моделей HDL выполните:

```bash
python3 custom_components/buspro/tools/check_catalog_models.py
```

Помощник читает `custom_components/buspro/devices/official_models.json` и выводит:

- официальные модели, отсутствующие в `DEVICE_CATALOG`
- модели каталога, отсутствующие в официальном списке
- виртуальные универсальные модели, используемые только интеграцией

Используйте строгий режим для проверок в стиле CI (ненулевой выход, если официальные модели
отсутствуют в каталоге):

```bash
python3 custom_components/buspro/tools/check_catalog_models.py --strict
```

## Поведение объектов

### Реле

Один общий координатор запрашивает статус реле один раз для каждого физического модуля и
распределяет ответ всем включенным объектам каналов. Отключенные каналы не подписываются и не
запрашивают шину.

### Панели

Известные панели кнопок создают один объект `event` для каждой физической кнопки, событие `Action`
и датчик `Last action`. Объекты событий кнопок пользовательского интерфейса представляют полученные
физические телеграммы кнопок Buspro; они не имитируют физическое нажатие.

### Диммеры

Поддерживаемые диммеры могут открывать подключение, максимальную яркость для каждого канала,
тип нагрузки и сообщаемую протоколом минимальную яркость. `Not reported` означает, что
устройство вернуло дозорный сигнал протокола вместо полезного значения.

### Контроллер логики

`HDL-MCLog.431` открывает только чтение подключения, версию встроенного ПО, последнее появление
и объекты событий логики. Некоторое встроенное ПО не отвечает на стандартный запрос встроенного ПО;
в этом случае объект встроенного ПО остается недоступным. Блоки логики не записываются, потому что
их изменение может перезаписать программирование контроллера.

## Сервисы

- `buspro.activate_scene`
- `buspro.set_universal_switch`
- `buspro.send_message`

`buspro.send_message` отправляет команду необработанного протокола и должна использоваться только с
проверенным кодом операции HDL и полезной нагрузкой.

## Конфигурация YAML (устаревшая)

Конфигурация устройства YAML полностью поддерживается наряду с управлением шлюзом записи конфигурации. Вы можете определить lights, covers, switches, fans, climate, sensors и binary_sensors через YAML, пока шлюз управляется интеграцией пользовательского интерфейса.

**Примечание**: Новые устройства должны использовать пользовательский интерфейс **Конфигурация > Добавить устройство** вместо YAML, так как он обеспечивает группировку устройств, управляемые моделью возможности и управление состоянием канала. YAML рекомендуется для:
- Устройства с нестандартными или устаревшими профилями
- Миграция со старых интеграций Buspro
- Сложная автоматизация или шаблоны датчиков

### Пример синтаксиса YAML

Добавьте в ваш `configuration.yaml`:

```yaml
light:
  - platform: buspro
    devices:
      "1.5.1":
        name: "Ceiling light"
        dimmable: true
      "1.5.2":
        name: "Wall lamp"
        dimmable: false

cover:
  - platform: buspro
    devices:
      "2.10.1":
        name: "Living room curtain"
        running_time: 45

climate:
  - platform: buspro
    devices:
      "3.1":
        name: "Bedroom climate"
        profile: "ac"
```

### Конфигурация платформы

Каждая платформа (`light`, `cover`, `fan`, `climate`, `sensor`, `binary_sensor`, `switch`) принимает:

| Ключ | Тип | Описание |
| --- | --- | --- |
| `devices` | dict | Обязательно. Отображение адресов Buspro на конфигурации устройств. |
| `running_time` | int | Время перехода по умолчанию в секундах (0 = без перехода). Переопределено для каждого устройства. |
| `ack_retry_enabled` | bool | Повторная отправка при отсутствии ACK (стандартное значение платформы; переопределения для каждого устройства). |

Каждый ключ устройства — это **адрес Buspro** в формате:
- **Light, cover, fan, switch**: `subnet.device.channel` (например, `1.5.2`)
- **Climate, sensor, binary_sensor**: `subnet.device` (например, `3.1`)

Каждая конфигурация устройства поддерживает:
- `name` (обязательно): Отображаемое имя
- `running_time`, `dimmable`, `ack_retry_enabled` (зависит от платформы, опционально)
- `profile` (опционально, для датчиков климата — например, `"ac"`, `"floor_heating"`)
- `object_id` (опционально): Slug идентификатора объекта
- `unique_id` (опционально): Для ручного управления реестром объектов
