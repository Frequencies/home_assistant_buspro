## Перше налаштування

### Конфігурація шлюзу
1. Відкрийте **Параметри > Пристрої та послуги > Додати інтеграцію** й оберіть
   **HDL Buspro**.
2. Введіть хост шлюзу та UDP-порти. Порт `6000` — це звичайне значення за замовчуванням.
3. Введіть невикористовувану адресу Buspro Home Assistant у форматі `subnet.device`.
   За замовчуванням це `200.200`; вона не повинна належати іншому пристрою Buspro.

### Додавання пристроїв
Після завершення налаштування шлюзу:

1. Відкрийте **Параметри > Пристрої та послуги > HDL Buspro > Налаштування**.
2. Натисніть **Додати пристрій**, щоб додати фізичний модуль Buspro.
3. **Оберіть тип пристрою** (Реле, Диммер, Штора, Клімат, Датчик тощо).
4. **Оберіть точну модель**, яка відповідає вашому обладнанню.
5. **Введіть адресу Buspro** у форматі `subnet.device` (наприклад, `1.5`).
6. **Введіть назву пристрою** (наприклад, «Світло вітальні»).
7. **Назвіть кожен канал** — залиште порожнім, щоб вимкнути канал.
8. Натисніть **Зберегти**.

Home Assistant автоматично групує сутності за фізичним модулем у реєстрі пристроїв.

**Для прикладів конфігурації UI та YAML для всіх типів пристроїв див. [DEVICE_EXAMPLES.md](docs/en/DEVICE_EXAMPLES.md).**

### Редагування пристроїв

Щоб змінити існуючий пристрій, відкрийте **Налаштування > Редагувати пристрій**. Ви можете:
- Перейменувати пристрій
- Перейменувати, увімкнути або вимкнути окремі канали
- Змінити модель (що може змінити кількість каналів)
- Видалити пристрій повністю

Пристрої, керовані UI, підтримують повне редагування. Застарілі YAML-пристрої можуть відкривати елементи керування назвами реєстру, але їхню конфігурацію протоколу все одно потрібно змінювати в YAML. Перезавантажте Home Assistant після зміни YAML.

### Швидкий приклад: додавання 4-канального модуля реле

1. Модель: `HDL-MR0410.431` (4 канали реле)
2. Адреса Buspro: `1.10`
3. Назва пристрою: «Реле кімнати»
4. Назви каналів: «Світло стелі», «Настінна лампа», «», «Вентилятор»
5. Натисніть **Зберегти**

Home Assistant автоматично створює сутності: `light.room_relays_ceiling_light`, `light.room_relays_wall_lamp`, `switch.room_relays_fan`

Для повних прикладів UI та YAML для всіх типів пристроїв див. **[DEVICE_EXAMPLES.md](docs/en/DEVICE_EXAMPLES.md)**.

Інтеграція buspro підтримує як **налаштування через UI**, так і **конфігурацію YAML**:

### Налаштування через UI
Найпростіший спосіб додати пристрої — див. **[DEVICE_EXAMPLES.md](docs/en/DEVICE_EXAMPLES.md)** для пошагових прикладів усіх типів пристроїв.

### Конфігурація YAML  
Інтеграція підтримує два взаємодоповнюючих підходи YAML:

- **Зосереджена на пристроях** (сучасна) — повні визначення пристроїв зі всіма каналами

## Критичні зміни в 2.2.0

Прочитайте цей розділ перед оновленням з 2.1.x.

> [!WARNING]
> Цей випуск змінює власництво пристроїв, створення каналів, семантику
> подій панелі та вбудований конструктор Python. Завершіть контрольний
> список оновлення перед видаленням застарілого YAML.

1. **Пристрої, спеціальні для установки, більше не вбудовані в інтеграцію.**
   Адреси пристроїв, назви, призначення каналів та кількість пристроїв тепер
   належать до параметрів запису конфігурації або реєстру пристроїв Home Assistant.
   Каталог пристроїв містить лише можливості обладнання.

2. **Модулі реле, керовані UI, використовують кількість своїх фізичних каналів.**
   `HDL-MR1210.433` завжди відкриває 12 гнізд каналів і
   `HDL-MR1610.433` завжди відкриває 16. Існуючий пристрій не можна зменшити
   нижче кількості фізичних каналів його моделі.

3. **Порожня назва каналу вимикає канал.**
   Вимкнені канали не інстанціюються, не створюють об'єкти протоколу та
   позначаються як вимкнені інтеграцією в реєстрі сутностей. Введення
   назви знову вмикає канал.

4. **Точна модель керує створеними сутностями.**
   Загальна панель `HDL` не має відомої кількості кнопок. Оберіть фізичну модель
   для створення подій кнопок. Зміна моделі перезавантажує запис конфігурації.

5. **Home Assistant має свою власну адресу Buspro.**
   Існуючі записи конфігурації переходять на `200.200`. Ця адреса повинна бути
   невикористовуваною в мережі Buspro та може бути змінена в **Налаштування > Параметри шлюзу**.

6. **IP-адреса джерела пакета більше не жорстко закодована.**
   Інтеграція отримує її з маршруту до налаштованого шлюзу. Хост Home Assistant
   з кількома інтерфейсами повинен маршрутизувати шлюз через
   призначений інтерфейс локальної мережі.

7. **События дій панелі тепер декодуються.**
   Автоматизацію, що спожива старі неопрацьовані значення дій, слід перевірити. События
   використовують `channel_on`, `channel_off`, `channel_level`, `scene`,
   `universal_switch_on` або `universal_switch_off`, з цільовими та зведеними
   атрибутами, де їх можна розрізнити.

8. **Вбудований API Python змінився.**
   Прямі користувачі `pybuspro.Buspro` повинні надати `client_address`; див.
   [pybuspro/README.md](pybuspro/README.md).

Інтеграція все ще читає застарілі сутності YAML під час переносу. Не тримайте
той самий фізичний канал як у конфігурації YAML, так і в керованій UI конфігурації,
оскільки це може створити дублювання сутностей і дублювання підписок протоколу.

## Контрольний список оновлення

1. Перезавантажте Home Assistant після заміни спеціального компонента.
2. Відкрийте **Параметри > Пристрої та послуги > HDL Buspro > Налаштування**.
3. Перевірте хост шлюзу, порти та невикористовувану адресу Buspro Home Assistant.
4. Відкрийте кожен фізичний пристрій і оберіть його точну модель.
5. Перевірте кожну назву каналу реле. Порожні канали навмисне залишаються вимкненими.
6. Перевірте автоматизацію, яка спожива события дій панелі.
7. Видаліть або прокоментуйте перенесені сутності YAML лише після того, як їхні замінники, керовані UI, збережуть очікувані ідентифікатори сутностей.

## Налаштування шлюзу

Додайте **HDL Buspro** з **Параметри > Пристрої та послуги** та налаштуйте:

- **Хост**: ім'я хосту шлюзу HDL IP або адреса IPv4.
- **Порт**: основний UDP-порт, зазвичай `6000`.
- **UDP порти прийому/передачі**: змінюйте їх лише для нестандартного шлюзу.
- **Адреса Buspro Home Assistant**: невикористовувана ідентичність `subnet.device`, така як стандартне значення переносу `200.200`.

UDP не має рукостиснення з'єднання. Налаштування перевіряє розпізнавання адрес, маршрутизацію та створення локального сокету прийому без припущення, що пристрій існує за жорстко закодованою адресою Buspro.

## Управління пристроями

Відкрийте **Налаштування** в інтеграції та оберіть:

- **Параметри шлюзу** для оновлення параметрів мережі та ідентичності клієнта.
- **Додати пристрій** для вибору типу пристрою, моделі, адреси Buspro та назв каналів або можливостей.
- **Редагувати пристрій** для перейменування каналів, вмикання або вимкнення каналів, видалення пристрою, керованого UI, або виправлення моделі існуючого пристрою реєстру.

Фізичні адреси відображаються в Home Assistant як серійний номер пристрою.
Сутності, що належать одному фізичному модулю, прикріплені до однієї запису в реєстрі пристроїв.

## Помічник обслуговування каталогу

Щоб порівняти каталог інтеграції з перевіреним офіційним списком моделей HDL, виконайте:

```bash
python3 custom_components/buspro/tools/check_catalog_models.py
```

Помічник читає `custom_components/buspro/devices/official_models.json` та виводить:

- офіційні моделі, відсутні в `DEVICE_CATALOG`
- моделі каталогу, відсутні в офіційному списку
- віртуальні загальні моделі, спеціальні для інтеграції

Використовуйте режим strict для перевірок у стилі CI (ненульовий вихід, коли офіційні моделі відсутні в каталозі):

```bash
python3 custom_components/buspro/tools/check_catalog_models.py --strict
```

## Поведінка сутностей

### Реле

Один спільний координатор опитує статус реле один раз на фізичний модуль та розповсюджує відповідь на всі активовані сутності каналів. Вимкнені канали не підписуються на шину та не запитують її.

### Панелі

Відомі кнопкові панелі створюють одну сутність `event` на фізичну кнопку, подію `Action` та датчик `Last action`. Сутності подій кнопок UI представляють отримані телеграми фізичної кнопки Buspro; вони не імітують натиск обладнання.

### Диммери

Підтримувані диммери можуть відкривати підключення, максимальну яскравість на канал, тип навантаження та мінімальну яскравість, про яку повідомляє протокол. `Not reported` означає, що пристрій повернув дозорний протокол замість придатного значення.

### Логічний контролер

`HDL-MCLog.431` відкриває доступ на читання для підключення, версії мікропрограми, останнього разу на зв'язку та сутностей события логіки. Деяка мікропрограма не відповідає на стандартний запит мікропрограми; у цьому випадку сутність мікропрограми залишається недоступною. Логічні блоки не можна писати, оскільки їхня зміна може перезаписати програмування контролера.

## Послуги

- `buspro.activate_scene`
- `buspro.set_universal_switch`
- `buspro.send_message`

`buspro.send_message` відправляє команду сирого протоколу та має використовуватися лише з перевіреним кодом операції HDL та корисним навантаженням.

## Конфігурація YAML (застаріла)

Конфігурація пристроїв YAML повністю підтримується поряд з управлінням шлюзом записами конфігурації. Ви можете визначити світила, штори, перемикачі, вентилятори, клімат, датчики та бінарні датчики через YAML, поки шлюзом керує UI інтеграції.

**Примітка**: Нові пристрої повинні використовувати UI інтеграції **Налаштування > Додати пристрій** замість YAML, оскільки він забезпечує групування пристроїв, можливості, керовані моделлю, та управління станом каналу. YAML рекомендується для:
- Пристроїв з нестандартними або застарілими профілями
- Переносу зі старіших інтеграцій Buspro
- Складної автоматизації або шаблонів датчиків

### Приклад синтаксису YAML

Додайте до вашого `configuration.yaml`:

```yaml
light:
  - platform: buspro
    devices:
      "1.5.1":
        name: "Ceiling light"
        dimmable: true
      "1.5.2":
        name: "Wall lamp"
        dimmable: false

cover:
  - platform: buspro
    devices:
      "2.10.1":
        name: "Living room curtain"
        running_time: 45

climate:
  - platform: buspro
    devices:
      "3.1":
        name: "Bedroom climate"
        profile: "ac"
```

### Конфігурація платформи

Кожна платформа (`light`, `cover`, `fan`, `climate`, `sensor`, `binary_sensor`, `switch`) приймає:

| Ключ | Тип | Опис |
| --- | --- | --- |
| `devices` | dict | Обов'язковий. Відображення адрес Buspro на конфігурації пристроїв. |
| `running_time` | int | Час переходу за замовчуванням у секундах (0 = без переходу). Перевизначено для кожного пристрою. |
| `ack_retry_enabled` | bool | Повторити передачу при відсутності ACK (стандартна платформа; перевизначення для кожного пристрою). |

Кожен ключ пристрою є **адресою Buspro** у форматі:
- **Light, cover, fan, switch**: `subnet.device.channel` (наприклад, `1.5.2`)
- **Climate, sensor, binary_sensor**: `subnet.device` (наприклад, `3.1`)

Кожна конфігурація пристрою підтримує:
- `name` (обов'язковий): Ім'я для відображення
- `running_time`, `dimmable`, `ack_retry_enabled` (специфічні для платформи, опціонально)
- `profile` (опціонально, для датчиків клімату — наприклад, `"ac"`, `"floor_heating"`)
- `object_id` (опціонально): Слаг ID сутності
- `unique_id` (опціонально): Для ручного керування реєстром сутностей
