# HDL Buspro для Home Assistant

[English](../../README.md) | **Беларуская**

Інтэграцыя кіруе шлюзам і фізічнымі прыладамі HDL Buspro праз інтэрфейс
Home Assistant. Поўны пералік мадэляў, сутнасцей і сэрвісаў глядзіце ў
[англійскай дакументацыі](../README.md).

## Усталяванне

### HACS (рэкамендуецца)

1. Адкрыйце **HACS > Інтэграцыі**.
2. Адкрыйце меню з трыма кропкамі і выберыце **Звычайныя сховішчы**.
3. Дабавьце `https://github.com/Frequencies/home_assistant_buspro` з катэгорыяй
   **Інтэграцыя**.
4. Шукайце **HDL Buspro**, адкрыйце яе і выберыце **Спампаваць**.
5. Перазапусціце Home Assistant, калі HACS гэта прапануе.

Будучыя версіі можна ўсталяваць з **HACS > Інтэграцыі**.
Перазапусціце Home Assistant пасля кожнага абнаўлення інтэграцыі.

### Ручное усталяванне

1. Спампуйце сховішча інтэграцыі.
2. Скапіруйце яе каталог `custom_components/buspro` ў
   `/config/custom_components/buspro` у Home Assistant.
3. Перазапусціце Home Assistant.

## Першая наладка

### Наладка шлюза
1. Адкрыйце **Параметры > Прыстасаванні і сэрвісы > Дадаць інтэграцыю** і
   выберыце **HDL Buspro**.
2. Ўвядзіце хост шлюза і портны UDP. Звычайны порт — `6000`.
3. Ўвядзіце невыкарыстоўваны адрас Buspro для Home Assistant у фармаце
   `падсец.прыстасаванне`. Па змаўчанні `200.200`; ён не павінен
   прыналежаць іншаму прыстасаванню Buspro.

### Дадаванне прыстасаванняў
Пасля завяршэння наладкі шлюза:

1. Адкрыйце **Параметры > Прыстасаванні і сэрвісы > HDL Buspro > Наладка**.
2. Выберыце **Дадаць прыстасаванне** і выберыце тып (Рэле, Дымер, Вентыля, Шторка, і т.д.).
3. Выберыце мадэль (або **Уніфікаваны** для невядомых мадэляў з колькасцю каналаў).
4. Ўвядзіце адрас Buspro, імя прыстасавання і назвы каналаў (пустыя назвы адключаюць каналы).
5. Выберыце **Захаваць**.

Home Assistant аўтаматычна групіруе ўсе сутнасці пад адной запіссю рэстру.

**Для дэтальных прыкладаў наладкі UI і YAML для ўсіх тыпаў прыстасаванняў глядзіце [../en/DEVICE_EXAMPLES.md](../en/DEVICE_EXAMPLES.md).**

### Рэдагаванне прыстасаванняў

Каб змяніць існуючае прыстасаванне, адкрыйце **Наладка > Рэдагаваць
прыстасаванне**. Вы можаце:
- Переназваць прыстасаванне
- Переназваць, уключыць або адключыць асобныя каналы
- Змяніць мадэль (можа змяніць колькасць каналаў)
- Поўнасцю выдаліць прыстасаванне

Кіроўныя інтэрфейсам прыстасаванні падтрымліваюць поўнае рэдагаванне.
Састарэлыя прыстасаванні YAML могуць пацяшкаваць элементы кантролю імёнаў
рэстру, але іх конфігурацыя пратакола заўсёды павінна змяняцца ў YAML.
Перазапусціце Home Assistant пасля змяненняў YAML.

### Прыклад: Дадаванне 4-канальнага модуля рэле

1. Мадэль: `HDL-MR0410.431` (4 рэле-каналы)
2. Адрас Buspro: `1.10`
3. Імя прыстасавання: "Рэле кімнаты"
4. Імёны каналаў:
   - Канал 1: "Потолочны светло"
   - Канал 2: "Настенны лямпа"
   - Канал 3: "" (адключыць)
   - Канал 4: "Вентыля"

Пасля захавання Home Assistant стварыць:
- `light.room_relays_ceiling_light`
- `light.room_relays_wall_lamp`
- `switch.room_relays_fan`

Поўныя прыклады UI і YAML для ўсіх тыпаў прыстасаванняў см. **[../en/DEVICE_EXAMPLES.md](../en/DEVICE_EXAMPLES.md)**.

## Параметры конфігурацыі

Інтеграцыя buspro падтрымлівае як **наладку праз інтэрфейс**, так і **конфігурацыю YAML**:

### Наладка праз інтэрфейс
Найзручніший спосаб дадання прыстасаванняў — см. **[../en/DEVICE_EXAMPLES.md](../en/DEVICE_EXAMPLES.md)** для пакроковых прыкладаў ўсіх тыпаў прыстасаванняў.

Інтеграцыя падтрымлівае два дадатковы падходы YAML:
- **На аснове сутнасці** (Legacy) — асобныя файлы сутнасцей, арганізаваныя па дзёменах
- **На аснове прыстасавання** (Modern) — поўныя вызначэнні прыстасаванняў з усімі каналамі

**Для поўнай дакументацыі YAML, прыкладаў і найлепшых практык см. ## Крытычныя змены ў версіі 2.2.0

- Адрасы, імёны, колькасць прыстасаванняў і прызначэнні каналаў больш не
  вбудаваны ў інтэграцыю. Яны захоўваюцца ў опцыях запісы канфігурацыі.
- Дакладная мадэль вызначае фізічную колькасць каналаў і створаныя сутнасці.
- Канал без імя адключаны і не створаецца.
- Адрас Buspro Home Assistant перенесены па змаўчанні на `200.200`. Гэты
  адрас павінен быць свабодны ў сеці.
- Падзеі панэлі тыпер дэкодуюцца як `channel_on`, `channel_off`,
  `channel_level`, `scene` і падзеі ўнівэрсальнага перамыкача.
- Убудаваны канструктар `Buspro` тыпер патрабуе `client_address`.

## Абнаўленне

1. Перазапусціце Home Assistant пасля замены кампанента.
2. Адкрыйце **Параметры > Прыстасаванні і сэрвісы > HDL Buspro > Наладка**.
3. Праверце шлюз, портны UDP і невыкарыстоўваны адрас Buspro для Home Assistant.
4. Выберыце дакладную мадэль для кожнага прыстасавання і праверце імёны
   каналаў.
5. Праверце аўтаматызацыі, якія выкарыстоўваюць падзеі панэлі.
6. Выдаліце або закаментуйце старыя сутнасці YAML толькі пасля праверкі
   іх замен, кіроўных інтэрфейсам.

Не наладжвайце адзін і тот жа фізічны канал адначасова ў YAML і праз
інтэрфейс. Гэта стварыць дублюючыяся сутнасці і подпіскі на пратакол.

## YAML-конфігурацыя (састарэла)

Конфігурацыя прыстасаванняў YAML поўнасцю падтрымліваецца разам з кіраваннем
шлюза праз запіс конфігурацыі. Вы можаце вызначаць светлы, шторкі,
перамыкачы, вентыля, клімат-кантроль, датчыкі і бінарныя датчыкі праз
YAML, калі шлюз кіруецца інтэрфейсам інтэграцыі.

**Заўвага**: Новыя прыстасаванні павінны выкарыстоўваць інтэрфейс
**Наладка > Дадаць прыстасаванне** замест YAML, так як ён забяспечвае
групіроўку прыстасаванняў, кіроўныя мадэллю магчымасці і кіраванне
станам канала. YAML рэкамендуецца для:
- Прыстасаванняў з нестандартнымі ці састарэлымі профілямі
- Міграцыі з іх старых інтэграцый Buspro
- Сложнай аўтаматызацыі ці шаблонаў датчыкаў

### Прыклад сінтаксісу YAML

Дабавьце ў ваш `configuration.yaml`:

```yaml
light:
  - platform: buspro
    devices:
      "1.5.1":
        name: "Потолочны светло"
        dimmable: true
      "1.5.2":
        name: "Настенны лямпа"
        dimmable: false

cover:
  - platform: buspro
    devices:
      "2.10.1":
        name: "Шторка гостьнай"
        running_time: 45

climate:
  - platform: buspro
    devices:
      "3.1":
        name: "Клімат спальні"
        profile: "ac"
```

### Конфігурацыя платформы

Кожная платформа (`light`, `cover`, `fan`, `climate`, `sensor`, `binary_sensor`,
`switch`) прымае:

| Ключ | Тып | Апісанне |
| --- | --- | --- |
| `devices` | dict | Абавязкова. Адлюстраванне адрасаў Buspro на конфігурацыі прыстасаванняў. |
| `running_time` | int | Час пераходу па змаўчанні ў секундах (0 = без пераходу). Перавызначаецца за прыстасаванне. |
| `ack_retry_enabled` | bool | Паўтаўце адправку без ACK (стандарт платформы; перавызначаецца за прыстасаванне). |

Кожны ключ прыстасавання мае адрас **Buspro** у фармаце:
- **Светло, шторка, вентыля, перамыкач**: `падсец.прыстасаванне.канал` (напрыклад, `1.5.2`)
- **Клімат, датчык, бінарны датчык**: `падсец.прыстасаванне` (напрыклад, `3.1`)

Кожная конфігурацыя прыстасавання падтрымліває:
- `name` (абавязкова): Імя для адлюстравання
- `running_time`, `dimmable`, `ack_retry_enabled` (спецыфічна для платформы, факультатыўна)
- `profile` (факультатыўна, для датчыкаў клімата — напрыклад, `"ac"`, `"floor_heating"`)
- `object_id` (факультатыўна): Slug ID сутнасці
- `unique_id` (факультатыўна): Для ручнога кіравання рэстрам сутнасцей

## Наладка шлюза

Дадайце **HDL Buspro** з **Параметры > Прыстасаванні і сэрвісы** і наладзьце:

- **Хост**: імя хоста або IPv4-адрэс шлюза HDL.
- **Порт**: першарадны порт UDP, звычайна `6000`.
- **Порты адпраўлення/атримання UDP**: мяняйце толькі для нестандартнага шлюза.
- **Адрэс Buspro Home Assistant**: невыкарыстаны ідэнтыфікатар `subnet.device`, такі як міграцыйны па дзефолце `200.200`.

UDP не мае адкрыцця падлучэння. Наладка праверыць разрешэнне адрэса, маршрутызацыю і стварэнне мясцовага прымаючага сокета без адкрыцця адзінога прыстасавання па жорстка закадаванаму адрэсу Buspro.

## Кіраванне прыстасаваннямі

Адкрыйце **Наладка** ў інтэграцыі і выберыце:

- **Параметры шлюза** для абнаўлення сеціўных параметраў і ідэнтыфікатара кліента.
- **Дадаць прыстасаванне** для выбару типу прыстасавання, мадэлі, адрэса Buspro і назваў каналаў або магчымасцей.
- **Рэдагаваць прыстасаванне** для перейменавання каналаў, уключэння або вывключэння каналаў, выдалення кіраванага UI прыстасавання або выпраўлення мадэлі існуючага запісу рэестра.

Фізічныя адрэсы адлюстроўваюцца ў Home Assistant як сярыйны нумар прыстасавання. Сутнасці, якія належаць адному фізічнаму модулю, прымацаваны да адзінага запісу рэестра прыстасаваннямі.

Для старых прыстасаваннямі YAML інтэграцыя цяпер нармалізуе адсутнічыя профілі, выкарыстоўваючы метаданыя каталога мадэлей. Невядомыя мадэлі і неподтрымліваемыя радкі профіляў павідоміляюцца як папярэджанні пры запуску, а потым вяртаюцца да агульнай паводзіны `sensor_status` для захавання функцыянальнасці установкі.

## Памочнік па абслугоўванні каталога

Каб параўнаць каталог інтэграцыі з утрыманым афіцыйным спісам мадэлей HDL, запуціце:

```bash
python3 custom_components/buspro/tools/check_catalog_models.py
```

Памочнік чытае `custom_components/buspro/devices/official_models.json` і выводзіць:

- афіцыйныя мадэлі, адсутнічыя ў `DEVICE_CATALOG`
- мадэлі каталога, адсутнічыя ў афіцыйным спісе
- віртуальныя ўнівесальныя мадэлі толькі для інтэграцыі

Выкарыстоўвайце строгі рэжым для праверак CI-стылю (выход з ненулявым кодам, калі афіцыйныя мадэлі адсутнічаюць у каталога):

```bash
python3 custom_components/buspro/tools/check_catalog_models.py --strict
```

## Паводзіна сутнасцей

### Рэле

Адзін агульны каардынатар запытвае стан рэле адзін раз для кожнага фізічнага модуля і размяркоўвае адказ на ўсе сутнасці ўключанага канала. Выключаныя каналы не падпісваюцца і не запытваюць шину.

### Панэлі

Вядомыя кнопкавыя панэлі ствараюць адну сутнасць `event` для кожнай фізічнай кнопкі, подзею `Action` і дачнік `Last action`. Сутнасці подзей кнопак UI прадстаўляюць атрыманыя фізічныя тэлеграмы кнопак Buspro; яны не імітуюць апаратнае натыск.

### Дымеры

Падтрымліваемыя дымеры могуць прадастаўляць падлучэнне, максімальную яскравасць кожнага канала, тып нагрузкі і мінімальную яскравасць, аб якой паведаміляе пратакол. `Not reported` азначае, што прыстасаванне вярнула дозорны пратакол замест выкарыстаннага значэння.

### Кантролер логікі

`HDL-MCLog.431` прадастаўляе доступ толькі для чытання да падлучэння, версіі прашівы, апошняга праглада і сутнасцей подзей логікі. Некаторая прашівая не адказвае на стандартны запыт прашівы; у гэтым выпадку сутнасць прашівы застаецца недаступнай. Логічныя блокі не запісваюцца, бо іх змена можа перезапісаць праграмаванне кантролера.

## Сэрвісы

- `buspro.activate_scene`
- `buspro.set_universal_switch`
- `buspro.send_message`

`buspro.send_message` адпраўляе сырую каманду пратакола і павінна выкарыстоўвацца толькі з праверенным HDL-кодам аперацыі і палезным грузам.

## Разробка

### Запуск тэставання набораў

З каталога конфігурацыі Home Assistant:

```bash
# Запусціце ўсе тэсты пратакола (19 тэстаў)
python3 -m unittest discover -s custom_components/buspro/tests/buspro_protocol -v

# Запусціце ўсе тэсты інтэграцыі (18 тэстаў)
python3 -m unittest discover -s custom_components/buspro/tests/buspro_integration -v

# Або запусціце асобныя файлы тэстаў
python3 custom_components/buspro/tests/buspro_protocol/test_sensor_protocol.py
python3 custom_components/buspro/tests/buspro_protocol/test_relay_coordinator.py
python3 custom_components/buspro/tests/buspro_protocol/test_logic_controller_protocol.py
python3 custom_components/buspro/tests/buspro_protocol/test_config_isolation.py
python3 custom_components/buspro/tests/buspro_protocol/test_device_lifecycle.py
python3 custom_components/buspro/tests/buspro_integration/test_device_catalog.py
python3 custom_components/buspro/tests/buspro_integration/test_managed_device_logic.py
python3 custom_components/buspro/tests/buspro_integration/test_model_notes_logging.py
python3 custom_components/buspro/tests/buspro_integration/test_yaml_normalization.py
```

Тэсты пратакола охоплюють аналіз тэлеграм, каардынацыю прыстасаванняў і
бяспеку асноўных задач/зваротных вызываў. Тэсты інтэграцыі охоплюють
каталог прыстасаванняў, логіку кіроўных прыстасаванняў, нармалізацыю YAML
і адстежыванне падтрымкі мадэляў.
