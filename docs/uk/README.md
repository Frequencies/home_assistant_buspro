Інтеграція керує шлюзом і фізичними пристроями HDL Buspro через інтерфейс
Home Assistant. Повний перелік моделей, сутностей і сервісів наведено в
[англійській документації](../README.md).

## Встановлення

### HACS (рекомендується)

1. Відкрийте **HACS > Інтеграції**.
2. Відкрийте меню з трьома точками і виберіть **Користувацькі репозиторії**.
3. Додайте `https://github.com/Frequencies/home_assistant_buspro` з категорією
   **Інтеграція**.
4. Пошукайте **HDL Buspro**, відкрийте її й виберіть **Завантажити**.
5. Перезавантажте Home Assistant, коли HACS це запропонує.

Майбутні версії можна встановлювати з **HACS > Інтеграції**.
Перезавантажуйте Home Assistant після кожного оновлення інтеграції.

### Ручне встановлення

1. Завантажте репозиторій інтеграції.
2. Скопіюйте його каталог `custom_components/buspro` у
   `/config/custom_components/buspro` в Home Assistant.
3. Перезавантажте Home Assistant.

## Перша настройка

### Конфігурація шлюза
1. Відкрийте **Параметри > Пристрої й сервіси > Додати інтеграцію** й
   виберіть **HDL Buspro**.
2. Введіть хост шлюза й порти UDP. Звичайний порт — `6000`.
3. Введіть невикористану адресу Buspro для Home Assistant у форматі
   `підмережа.пристрій`. За замовчуванням `200.200`; вона не повинна
   належати іншому пристрою Buspro.

### Додавання пристроїв
Після завершення конфігурації шлюза:

1. Відкрийте **Параметри > Пристрої й сервіси > HDL Buspro > Налаштування**.
2. Натисніть **Додати пристрій** для додавання фізичного модуля.
3. **Виберіть тип пристрою** (Реле, Диммер, Штора, Клімат, Сенсор тощо).
4. **Виберіть точну модель**, що відповідає вашому обладнанню.
5. **Введіть адресу Buspro** у форматі `підмережа.пристрій` (наприклад, `1.5`).
6. **Введіть назву пристрою** (наприклад, "Світло вітальні").
7. **Назвіть кожен канал** — залишіть пустим, щоб деактивувати канал.
8. Натисніть **Зберегти**.

Home Assistant автоматично групує сутності за фізичним модулем у реєстрі пристроїв.

**Детальні приклади конфігурації UI та YAML для всіх типів пристроїв див. [../en/DEVICE_EXAMPLES.md](../en/DEVICE_EXAMPLES.md).**

### Редагування пристроїв

Щоб змінити існуючий пристрій, відкрийте **Налаштування > Редагувати
пристрій**. Ви можете:
- Перейменувати пристрій
- Перейменувати, увімкнути або вимкнути окремі канали
- Змінити модель (може змінити кількість каналів)
- Повністю видалити пристрій

Керовані інтерфейсом пристрої підтримують повне редагування. Застарілі
пристрої YAML можуть надавати елементи керування найменуванням реєстру,
але їхня конфігурація протоколу все ще повинна змінюватися у YAML.
Перезавантажте Home Assistant після змін YAML.

### Приклад: Додавання 4-канального модуля реле

1. Модель: `HDL-MR0410.431` (4 канали реле)
2. Адреса Buspro: `1.10`
3. Назва пристрою: "Реле кімнати"
4. Назви каналів:
   - Канал 1: "Стельове світло"
   - Канал 2: "Настінна лампа"
   - Канал 3: "" (деактивовано)
   - Канал 4: "Вентилятор"

Після збереження Home Assistant створює:
- `light.room_relays_ceiling_light`
- `light.room_relays_wall_lamp`
- `switch.room_relays_fan`

Повні приклади UI та YAML для всіх типів пристроїв див. **[../en/DEVICE_EXAMPLES.md](../en/DEVICE_EXAMPLES.md)**.

## Критичні зміни у версії 2.2.0

- Адреси, назви, кількість пристроїв і призначення каналів більше не
  вбудовані в інтеграцію. Вони зберігаються в параметрах запису конфігурації.
- Точна модель визначає фізичну кількість каналів і створені сутності.
- Канал без назви деактивовано й не створюється.
- Адреса Buspro Home Assistant переносить за замовчуванням на `200.200`. Ця
  адреса повинна бути вільною в мережі.
- События панелі тепер декодуються як `channel_on`, `channel_off`,
  `channel_level`, `scene` та события універсального перемикача.
- Вбудований конструктор `Buspro` тепер потребує `client_address`.

## Оновлення

1. Перезавантажте Home Assistant після заміни компонента.
2. Відкрийте **Параметри > Пристрої й сервіси > HDL Buspro > Налаштування**.
3. Перевірте шлюз, порти UDP й невикористану адресу Buspro для Home Assistant.
4. Виберіть точну модель для кожного пристрою й перевірте назви каналів.
5. Перевірте автоматизації, які використовують события панелі.
6. Видаліть або закоментуйте старі сутності YAML лише після перевірки
   їхніх замін, керованих інтерфейсом.

Не налаштовуйте один і той же фізичний канал одночасно в YAML і через
інтерфейс. Це створить дублікаті сутності й підписки на протокол.

## YAML-конфігурація (застаріла)

Конфігурація пристроїв YAML повністю підтримується разом з керуванням
шлюзом через запис конфігурації. Ви можете визначати світильники, штори,
перемикачі, вентилятори, кліматичний контроль, датчики й бінарні датчики
через YAML, поки шлюз керується інтерфейсом інтеграції.

**Примітка**: Нові пристрої повинні використовувати інтерфейс
**Налаштування > Додати пристрій** замість YAML, оскільки він забезпечує
групування пристроїв, можливості, керовані моделлю, й управління станом
каналу. YAML рекомендується для:
- Пристроїв з нестандартними або застарілими профілями
- Міграції зі старших інтеграцій Buspro
- Складної автоматизації або шаблонів датчиків

### Приклад синтаксису YAML

Додайте до вашого `configuration.yaml`:

```yaml
light:
  - platform: buspro
    devices:
      "1.5.1":
        name: "Стельове світло"
        dimmable: true
      "1.5.2":
        name: "Настінна лампа"
        dimmable: false

cover:
  - platform: buspro
    devices:
      "2.10.1":
        name: "Штора вітальні"
        running_time: 45

climate:
  - platform: buspro
    devices:
      "3.1":
        name: "Клімат спальні"
        profile: "ac"
```

### Конфігурація платформи

Кожна платформа (`light`, `cover`, `fan`, `climate`, `sensor`, `binary_sensor`,
`switch`) приймає:

| Ключ | Тип | Опис |
| --- | --- | --- |
| `devices` | dict | Обов'язково. Відображення адрес Buspro на конфігурації пристроїв. |
| `running_time` | int | Час переходу за замовчуванням у секундах (0 = без переходу). Переопределяється за пристрій. |
| `ack_retry_enabled` | bool | Повторити надсилання без ACK (стандарт платформи; переопределяється за пристрій). |

Кожен ключ пристрою є **адресою Buspro** у форматі:
- **Світло, штора, вентилятор, перемикач**: `підмережа.пристрій.канал` (наприклад, `1.5.2`)
- **Клімат, датчик, бінарний датчик**: `підмережа.пристрій` (наприклад, `3.1`)

Кожна конфігурація пристрою підтримує:
- `name` (обов'язково): Назва для відображення
- `running_time`, `dimmable`, `ack_retry_enabled` (специфічно для платформи, факультативно)
- `profile` (факультативно, для датчиків клімату — наприклад, `"ac"`, `"floor_heating"`)
- `object_id` (факультативно): Слаг ID сутності
- `unique_id` (факультативно): Для ручного управління реєстром сутностей


## Налаштування шлюзу

Додайте **HDL Buspro** з **Параметри > Пристрої та служби** та налаштуйте:

- **Хост**: ім'я хоста або IPv4-адреса шлюзу HDL.
- **Порт**: основний порт UDP, зазвичай `6000`.
- **Порти відправлення/отримання UDP**: змінюйте тільки для нестандартного шлюзу.
- **Адреса Buspro Home Assistant**: невикористаний ідентифікатор `subnet.device`, такий як міграційний за замовчуванням `200.200`.

UDP не має рукостискання з'єднання. Налаштування перевіряє дозвіл адреси, маршрутизацію та створення локального приймального сокета без припущення про наявність пристрою за жорстко закодованою адресою Buspro.

## Управління пристроями

Відкрийте **Налаштування** в інтеграції та виберіть:

- **Параметри шлюзу** для оновлення параметрів мережі та ідентифікатора клієнта.
- **Додати пристрій** для вибору типу пристрою, моделі, адреси Buspro та назв каналів або можливостей.
- **Редагувати пристрій** для перейменування каналів, увімкнення або вимкнення каналів, видалення керованого UI пристрою або виправлення моделі існуючого запису реєстру.

Фізичні адреси відображаються в Home Assistant як серійний номер пристрою. Сутності, які належать одному фізичному модулю, прикріплені до одного запису реєстру пристроїв.

## Помічник із обслуговування каталогу

Щоб порівняти каталог інтеграції з офіційним списком моделей HDL, запустіть:

```bash
python3 custom_components/buspro/tools/check_catalog_models.py
```

Помічник читає `custom_components/buspro/devices/official_models.json` і виводить:

- офіційні моделі, відсутні в `DEVICE_CATALOG`
- моделі каталогу, відсутні в офіційному списку
- віртуальні універсальні моделі тільки для інтеграції

Використовуйте строгий режим для перевірок стилю CI (вихід з ненульовим кодом, коли офіційні моделі відсутні в каталозі):

```bash
python3 custom_components/buspro/tools/check_catalog_models.py --strict
```

## Поведінка сутностей

### Реле

Один спільний координатор запитує стан реле один раз на кожен фізичний модуль і розповсюджує відповідь на всі сутності увімкнутого каналу. Вимкнені канали не підписуються і не запитують шину.

### Панелі

Відомі кнопкові панелі створюють одну сутність `event` на кожну фізичну кнопку, подію `Action` та датчик `Last action`. Сутності подій кнопок UI представляють отримані фізичні телеграми кнопок Buspro; вони не імітують апаратне натиснення.

### Димери

Підтримувані димери можуть надавати підключення, максимальну яскравість кожного каналу, тип навантаження та мінімальну яскравість, про яку повідомляє протокол. `Not reported` означає, що пристрій повернув дозорний протокол замість використовуваного значення.

### Контролер логіки

`HDL-MCLog.431` надає доступ тільки для читання до підключення, версії прошивки, останнього перегляду та сутностей подій логіки. Деяка прошивка не відповідає на стандартний запит прошивки; в цьому випадку сутність прошивки залишається недоступною. Логічні блоки не можна записувати, оскільки їх зміна може перезаписати програмування контролера.

## Послуги

- `buspro.activate_scene`
- `buspro.set_universal_switch`
- `buspro.send_message`

`buspro.send_message` відправляє необроблену команду протоколу і повинна використовуватися тільки з перевіреним кодом операції HDL та корисним навантаженням.

## Конфігурація YAML (застарілий)

Конфігурація пристроїв YAML повністю підтримується поряд з управлінням шлюзом записів конфігурації. Ви можете визначати світильники, жалюзі, вимикачі, вентилятори, клімат, датчики та двійкові датчики через YAML, тоді як шлюз управляється інтерфейсом користувача інтеграції.

**Примітка**: Нові пристрої мають використовувати інтерфейс інтеграції **Налаштування > Додати пристрій** замість YAML, оскільки він забезпечує групування пристроїв, можливості, керовані моделлю, та управління станом каналу. YAML рекомендується для:
- Пристрої з нестандартними або застарілими профілями
- Міграція зі старих інтеграцій Buspro
- Складна автоматизація або шаблони датчиків

### Приклад синтаксису YAML

Додайте до вашого `configuration.yaml`:

```yaml
light:
  - platform: buspro
    devices:
      "1.5.1":
        name: "Ceiling light"
        dimmable: true
      "1.5.2":
        name: "Wall lamp"
        dimmable: false

cover:
  - platform: buspro
    devices:
      "2.10.1":
        name: "Living room curtain"
        running_time: 45

climate:
  - platform: buspro
    devices:
      "3.1":
        name: "Bedroom climate"
        profile: "ac"
```

### Конфігурація платформи

Кожна платформа (`light`, `cover`, `fan`, `climate`, `sensor`, `binary_sensor`, `switch`) приймає:

| Ключ | Тип | Опис |
| --- | --- | --- |
| `devices` | dict | Обов'язково. Відображення адрес Buspro на конфігурації пристроїв. |
| `running_time` | int | Час переходу за замовчуванням у секундах (0 = без переходу). Переопределяється для кожного пристрою. |
| `ack_retry_enabled` | bool | Повтор надіслань без ACK (стандарт платформи; переопределення для кожного пристрою). |

Кожен ключ пристрою - це **адреса Buspro** у форматі:
- **Світильник, жалюзі, вентилятор, вимикач**: `subnet.device.channel` (наприклад `1.5.2`)
- **Клімат, датчик, двійковий датчик**: `subnet.device` (наприклад `3.1`)

Кожна конфігурація пристрою підтримує:
- `name` (обов'язково): Отображувальне ім'я
- `running_time`, `dimmable`, `ack_retry_enabled` (специфічно для платформи, необов'язково)
- `profile` (необов'язково, для датчиків клімату — наприклад `"ac"`, `"floor_heating"`)
- `object_id` (необов'язково): Слаг ID сутності
- `unique_id` (необов'язково): Для ручного керування реєстром сутностей

### Запуск тестових наборів

З директорії конфігурації Home Assistant:

```bash
# Запустіть усі тести протоколу (19 тестів)
python3 -m unittest discover -s custom_components/buspro/tests/buspro_protocol -v

# Запустіть усі тести інтеграції (18 тестів)
python3 -m unittest discover -s custom_components/buspro/tests/buspro_integration -v

# Або запустіть окремі файли тестів
python3 custom_components/buspro/tests/buspro_protocol/test_sensor_protocol.py
python3 custom_components/buspro/tests/buspro_protocol/test_relay_coordinator.py
python3 custom_components/buspro/tests/buspro_protocol/test_logic_controller_protocol.py
python3 custom_components/buspro/tests/buspro_protocol/test_config_isolation.py
python3 custom_components/buspro/tests/buspro_protocol/test_device_lifecycle.py
python3 custom_components/buspro/tests/buspro_integration/test_device_catalog.py
python3 custom_components/buspro/tests/buspro_integration/test_managed_device_logic.py
python3 custom_components/buspro/tests/buspro_integration/test_model_notes_logging.py
python3 custom_components/buspro/tests/buspro_integration/test_yaml_normalization.py
```

Тести протоколу охоплюють аналіз телеграм, координацію пристроїв і
безпеку основних завдань/зворотних викликів. Тести інтеграції охоплюють
каталог пристроїв, логіку керованих пристроїв, нормалізацію YAML й
отримання даних про підтримку моделей.

## Підтвердження Команди (НОВЕ!)

Інтеграція тепер підтримує **опціональне підтвердження команди**, щоб гарантувати, що зміни стану пристрою відображаються в Home Assistant лише після того, як фізичний пристрій підтвердить отримання та виконання.

### Що це таке?

- **Без підтвердження:** Команди відправляються і інтерфейс оновлюється одразу (~5ms), але якщо пристрій не отримає команду через перешкоди в мережі, стан інтерфейсу буде невірним.
- **З підтвердженням:** Система чекає на підтвердження пристрою (100-500ms), забезпечуючи ідеальну синхронізацію між Home Assistant і фізичним пристроєм.

### Коли це використовувати?

Включіть підтвердження для:
- **Критичних пристроїв** — Реле аварійної зупинки, головні вимикачі
- **Ненадійних мереж** — Високі перешкоди, втрата пакетів
- **Залежностей автоматизації** — Коли автоматизація залежить від точного стану
- **Систем, критичних для безпеки** — HVAC, теплі підлоги, важливі навантаження

### Конфігурація

Додайте підтвердження до будь-якого пристрою в YAML:

```yaml
light:
  - platform: buspro
    devices:
      "1.10.1":
        name: "Критичне світло"
        enable_confirmation: true
        confirmation_timeout: 5.0        # секунди
        confirmation_retries: 3          # спроби повтору
```

**Параметри:**
- `enable_confirmation` (boolean, за замовчуванням: `false`) — Включити/вимкнути підтвердження
- `confirmation_timeout` (float, за замовчуванням: `5.0`) — Час очікування у секундах (0.1-60)
- `confirmation_retries` (integer, за замовчуванням: `3`) — Кількість повторів (0-10)

**Рекомендовані параметри за типами пристроїв:**
- Реле/Вимикач/Світло: `timeout: 5.0`, `retries: 3`
- Жалюзі/Штора: `timeout: 10.0`, `retries: 2` (механічне, повільніше)
- Клімат: `timeout: 5.0`, `retries: 3`
- Вентилятор: `timeout: 5.0`, `retries: 3`

Для повних прикладів і найкращих практик див. **[DEVICE_EXAMPLES.md](docs/uk/DEVICE_EXAMPLES.md)**.
